# Модель угроз этапа 4

## Цель

Защитить обмен управляющими RPC оверлейной сети от прослушивания, изменения сообщений, подмены NodeID и повторной обработки ранее принятого запроса.

## Защищаемые данные

- содержимое `PING`, `FIND_NODE`, `STORE`, `FIND_VALUE` и ответов;
- подтверждённая идентичность узла и соответствие сертификата его NodeID;
- однократная обработка каждого прикладного сообщения в окне защиты от повторов.

## Модель нарушителя

Предполагается, что нарушитель может наблюдать, задерживать, менять, удалять и повторно передавать сетевые пакеты, а также подключаться как посторонний клиент. Он не контролирует конечный процесс узла, его закрытый ключ Ed25519 или доверенный центр сертификации.

## Реализованные меры

| Угроза | Мера |
|---|---|
| Прослушивание или изменение данных | TLS 1.3 с проверкой целостности и шифрованием записей TLS |
| Подключение без сертификата доверенного узла | Обязательный взаимный TLS: сервер требует клиентский сертификат, клиент проверяет сертификат сервера |
| NodeID подменён в payload | NodeID из payload сравнивается с NodeID клиентского TLS-сертификата для FIND_NODE, FIND_VALUE и STORE |
| Сертификат содержит чужой NodeID | NodeID пересчитывается по Ed25519 открытому ключу, затем сравнивается с URI SAN сертификата |
| Сервер-контакт предъявляет другой NodeID | RPC-клиент сравнивает сертификат с ожидаемым NodeID, когда этот ID известен |
| Повтор сообщения в сессии или после её закрытия | Случайный `session_id`, последовательный counter и кэш уникальных message ID по NodeID на 10 минут |
| Повтор DHT-записи или откат версии | Сохраняются проверки Ed25519 подписи и монотонного `sequence_number` этапа 3 |
| Downgrade до TLS 1.2 или ранние 0-RTT данные | Контексты разрешают только TLS 1.3, TLS tickets/resumption отключены |

## Ограничения локальной конфигурации

Для удобного локального запуска на одном компьютере проект автоматически создаёт тестовый CA в `.state/authority` и выпускает сертификаты узлов. Закрытый ключ этого CA нужен коду для выдачи сертификатов. Его компрометация позволяет выпустить сертификат с чужой идентичностью. Поэтому текущую автоматическую выдачу нельзя считать схемой промышленного развёртывания или использовать для недоверенных удалённых компьютеров. В реальной многомашинной сети CA должен быть отдельной доверенной стороной: узлы получают только свой сертификат и закрытый ключ, а публичный CA сертификат; закрытый ключ CA хранится отдельно.

Кэш replay-защиты хранится в памяти процесса и очищает записи старше 10 минут. Перезапуск узла сбрасывает этот кэш. Повтор ранее наблюдавшегося TLS ciphertext не проходит новый handshake; приложение отдельно отбрасывает дубликаты сообщений, повторно отправленные внутри новой аутентифицированной TLS-сессии в пределах окна кэша.

Этап 4 не реализует туннелирование произвольного IP-трафика. Это отдельная задача следующего этапа.

## Проверки

Автоматические проверки находятся в `tests/test_secure_session.py` и `tests/test_find_node_rpc.py`: настройка TLS 1.3 и обязательного клиентского сертификата, соответствие сертификата NodeID, отказ сертификату с подставленным NodeID, отбрасывание повторного сообщения в той же и новой сессии, последовательность counter и отказ RPC payload, заявляющему чужой NodeID. Полный тестовый прогон также проверяет, что overlay RPC и DHT работают через защищённые соединения.
