# Архитектура защищённой оверлейной P2P-сети

## Назначение

Проект моделирует оверлейную сеть поверх TCP. Каждый процесс представляет отдельный узел и имеет собственные ключи, таблицу маршрутизации и DHT-хранилище. Центральный сервер каталогизации не используется: начальный контакт задаётся bootstrap-адресом, после чего узлы узнают контакты друг от друга.

## Выбранное проектное решение

- Уровень: оверлейная сеть адресных записей узлов с итеративной маршрутизацией Kademlia-подобного типа; передача произвольного IP-трафика через туннель не входит в этапы 1–4.
- Язык и библиотеки: Python 3.13; `asyncio`, `ssl`, TCP и JSON берутся из стандартной библиотеки; `cryptography` используется для Ed25519 и сертификатов; `pytest` — для тестов.
- Размер пилотной сети: `N = 5` узлов в автоматическом эксперименте поиска; ручная проверка защищённых RPC выполняется на трёх локальных узлах.
- Сериализация: компактный JSON в UTF-8 выбран за доступность в стандартной библиотеке и удобство проверки. MessagePack обычно компактнее, но требует дополнительной зависимости; измерительное сравнение относится к опциональному расширению.
- Настраиваемые параметры находятся в `config/default.json` и `config/pilot.json`. Порт задаётся аргументом командной строки, конфигурационный файл выбирается переменной `OVERLAY_CONFIG`.
- Этапы 1–4 охватывают транспорт и кадрирование, идентичность и поиск узлов, DHT адресных записей, а также TLS 1.3 и защиту от повторов. Автоматическое переопубликование DHT-записей и произвольный сетевой туннель не входят в текущий обязательный базовый результат.

## Подсистемы

| Подсистема | Реализация | Ответственность |
|---|---|---|
| Транспорт | `transport/frame.py`, `transport/tcp.py`, `secure_session.py` | Границы кадров, TLS 1.3 mutual authentication, идентичность сертификатов и защита от replay |
| Идентичность | `identity.py` | Ed25519-ключ, постоянный `NodeID`, подпись записей |
| Маршрутизация | `routing.py`, `lookup.py` | XOR-метрика, k-buckets и итеративный `FIND_NODE` |
| DHT-записи | `records.py`, `dht_store.py` | Каноническая запись владельца, проверка подписи, TTL и версии |
| DHT RPC | `protocol.py`, `rpc.py`, `dht.py` | `STORE`, репликация, итеративный `FIND_VALUE` |
| Параметры | `config/default.json`, `config.py` | Версия протокола, лимит кадра, тайм-ауты, параметры маршрутизации и DHT |
| Демонстрация | `demo.py` | Запуск узла и команд публикации/поиска для локального стенда |

## Потоки данных

### Публикация записи

Владелец формирует `NodeRecord` с адресами и `sequence_number`, подписывает канонические байты Ed25519 и вычисляет ключ DHT как `SHA-256("node:" || NodeID)`. Поиск ближайших узлов обновляет пул контактов. Публикатор упорядочивает известные контакты по XOR-расстоянию до ключа, пытается получить `R=3` подтверждения и считает публикацию успешной при наличии не менее двух.

### Поиск записи

Инициатор отправляет `FIND_VALUE` bootstrap-узлу или ближайшим известным контактам. Если узел хранит действующую запись, он возвращает её. Иначе возвращает до `k` ближайших известных контактов; поиск повторяется с этими контактами до нахождения записи или исчерпания кандидатов. Полученную запись проверяют по сроку действия, адресу, соответствию публичного ключа и `NodeID`, а также подписи.

## Состояние узла

В каталоге `--state-dir` сохраняются закрытый ключ идентичности и `dht_records.json`. Файл DHT хранит подписанные записи и наибольший принятый `sequence_number` для каждого ключа. После истечения TTL значение удаляется из выдачи, но номер версии сохраняется для отклонения отката. Каталоги состояния не следует включать в репозиторий или передавать другим пользователям.

## Защищённая сессия

Все прикладные RPC идут по TLS 1.3 с обязательным сертификатом клиента. Сертификат связан с Ed25519 NodeID через публичный ключ и URI SAN; ожидаемый NodeID контакта сверяется при его наличии. Для каждого прикладного запроса используется случайный `session_id`, счётчик и уникальный `request_id`. Сервер отклоняет повторные или неупорядоченные запросы в пределах окна replay-кэша. Подробности, включая ограничения локального тестового CA, приведены в `THREAT_MODEL.md`.

## Границы текущего этапа

Этап 4 защищает управляющий трафик и DHT RPC, но не реализует туннелирование произвольного IP-трафика; оно относится к следующему этапу. Переопубликование владельцем, периодическое обслуживание и псевдонимы остаются расширениями.
