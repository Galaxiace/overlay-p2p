# Спецификация прикладного протокола

## Общий кадр

Все сообщения передаются в TCP-кадре версии, заданной в `config/default.json` (по умолчанию версия 1). Заголовок занимает 24 байта и содержит `version` (1 байт), `type` (1 байт), `flags` (2 байта), `request_id` (16 байт) и `payload_length` (4 байта). Числа кодируются в сетевом порядке байтов. Payload управляющих сообщений — JSON в UTF-8; ключи JSON сериализуются в лексикографическом порядке без пробелов. По умолчанию максимальный payload — 65 536 байт.

| Код | Тип сообщения | Назначение |
|---:|---|---|
| 1 | `PING` | Проверка доступности узла |
| 2 | `PONG` | Ответ с тем же `request_id` |
| 3 | `FIND_NODE_REQUEST` | Запрос ближайших контактов к `target_node_id` |
| 4 | `FIND_NODE_RESPONSE` | Идентичность ответившего узла и список контактов |
| 5 | `STORE_REQUEST` | Передача подписанного `NodeRecord` хранителю |
| 6 | `STORE_RESPONSE` | Принятие/отклонение записи и текущая версия |
| 7 | `FIND_VALUE_REQUEST` | Запрос значения по 32-байтовому DHT-ключу |
| 8 | `FIND_VALUE_RESPONSE` | Запись, если она есть, иначе ближайшие контакты |
| 255 | `ERROR` | Ошибка обработки запроса |

Ответ должен содержать тот же `request_id`, что и соответствующий запрос. RPC-клиент отклоняет ответ с другим идентификатором; negative-тест этой проверки находится в `tests/test_find_node_rpc.py`.

## Защищённый транспорт (этап 4)

Все overlay RPC (`PING`, `FIND_NODE`, `STORE`, `FIND_VALUE`) передаются только внутри TLS 1.3. Узел одновременно предъявляет сертификат клиента и проверяет сертификат удалённого узла. Контексты ограничивают минимум и максимум TLS версией 1.3; TLS 1.2 и TLS 0-RTT не используются, возобновление сессий TLS отключено.

В сертификате узла находится Ed25519 открытый ключ, из которого вычисляется NodeID. Subject Alternative Name содержит `urn:overlay:node:<NodeID>` и DNS имя `overlay-node`. После TLS handshake приложение повторно проверяет, что NodeID в SAN совпадает с NodeID, вычисленным из ключа сертификата. Ожидаемый NodeID контакта дополнительно сверяется, если он известен из таблицы маршрутизации. Подписанные DHT-записи дополнительно проверяются прежним способом.

Внутри TLS каждый прикладной кадр оборачивается кадром типа `254`. Его payload имеет вид `session_id[16] || counter[8] || encoded_inner_frame`. `session_id` генерируется криптографическим генератором случайных чисел. Первый запрос использует счётчик `0`, ответ — `1`. Внутренний `request_id` является уникальным `message_id` и обязан совпадать с ID внешнего кадра. Приёмник проверяет последовательность счётчиков и хранит использованные ID сообщений по аутентифицированному NodeID в течение 10 минут; повтор или нарушение порядка отклоняется.

Репозиторий создаёт тестовый центр сертификации и сертификаты узлов в `.state/authority` и `.state/tls`. Такая схема предназначена для локальной проверки на одном компьютере. В многомашинной среде доверенный CA должен выпускать сертификат каждому узлу; закрытый ключ CA нельзя распространять вместе с узлами. Детали и ограничения описаны в `THREAT_MODEL.md`.

## NodeRecord

Упрощённый уровень публикует адресную запись только по `NodeID`; псевдонимы в текущем этапе не используются. Ключ записи:

```text
DHT_KEY = SHA-256(ASCII("node:") || NODE_ID_32_BYTES)
```

Пример JSON-полей:

```json
{
  "addresses": [{"host": "127.0.0.1", "port": 9001}],
  "expires_at": 1800000180,
  "identity_public_key": "<64 hex-символа>",
  "issued_at": 1800000000,
  "node_id": "<64 hex-символа>",
  "sequence_number": 1,
  "signature": "<128 hex-символов>"
}
```

`issued_at` и `expires_at` — целые секунды Unix time. `sequence_number` — неотрицательное целое число, увеличиваемое владельцем при каждой новой публикации. Допускается от 1 до 8 уникальных пар адреса. `host` — IP-адрес, `localhost` или DNS-имя; `port` лежит в диапазоне 1–65535. Максимальный размер сериализованной записи — 4096 байт.

Для подписи поле `signature` исключается. Остальные поля сериализуются как ASCII JSON с отсортированными ключами, без пробелов, с обычным JSON-кодированием строк. Подписываемая последовательность:

```text
ASCII("overlay-p2p/node-record/v1\0") || CANONICAL_JSON(unsigned NodeRecord)
```

Подпись — Ed25519 подпись этой последовательности ключом, соответствующим `identity_public_key`. `node_id` должен совпадать с идентификатором, вычисленным из открытого ключа по алгоритму этапа 2.

TTL записи должен составлять от 120 до 300 секунд. Хранитель проверяет подпись, соответствие NodeID и открытого ключа, адреса, размер, диапазон TTL и то, что `expires_at` ещё не наступил. Для одного DHT-ключа принимается только запись с большим `sequence_number`. Повтор той же записи идемпотентен; другая запись с тем же номером и запись с меньшим номером отклоняются. После истечения TTL запись не выдаётся, однако сохранённый максимальный номер версии остаётся для защиты от отката.

## STORE

Payload `STORE_REQUEST` — JSON `NodeRecord`. Хранитель проверяет и сохраняет запись. Ответ `STORE_RESPONSE` содержит:

```json
{"accepted": true, "highest_sequence": 1, "reason": ""}
```

Публикатор выбирает ближайшие доступные контакты по XOR-расстоянию до `DHT_KEY`, стремится получить `R=3` подтверждения и считает операцию успешной при `quorum=2` или более. Недоступный контакт пропускается; следующая ближайшая доступная реплика может занять его место.

## FIND_VALUE

Payload `FIND_VALUE_REQUEST` содержит `sender_node_id`, `sender_public_key`, `sender_listen_port` и `dht_key`. Получатель проверяет соответствие ключа и NodeID. Если значение найдено и TTL не истёк, `FIND_VALUE_RESPONSE` возвращает `record`. Иначе `record` равен `null`, а `contacts` содержит не более `k` ближайших контактов. Инициатор проверяет найденную запись и продолжает итеративный поиск по контактам, пока значение не будет найдено либо кандидаты не закончатся.
