# Защищённая оверлейная P2P-сеть

Прототип защищённой оверлейной сети на основе P2P-протоколов. Реализованы TCP-кадрирование, идентичность Ed25519, маршрутизация Kademlia-подобного типа, DHT (подписанные записи, STORE/FIND_VALUE, TTL, защита от отката и репликация), а также защищённые RPC этапа 4 на TLS 1.3 с взаимной аутентификацией и защитой от replay.

## Требования

- Windows 11 x64
- Python 3.13.16 (64-bit)
- PyCharm Community или Professional

Параметры узлов вынесены в два JSON-профиля: `config/default.json` — обычный, `config/pilot.json` — с увеличенными тайм-аутами для более медленной машины. Чтобы использовать профиль пилотной сети в PowerShell, задайте `$env:OVERLAY_CONFIG = ".\config\pilot.json"` перед запуском. Узлы одной сети должны использовать одинаковые значения `protocol_version`, `max_frame_payload`, `k_bucket_size`, `alpha`, `replication_factor` и параметров DHT. Порт задаётся аргументом `--port` без изменения кода.

Проектное решение, размер пилотной сети и границы этапов зафиксированы в `ARCHITECTURE.md`. Пилот поиска использует пять узлов; ручная демонстрация защищённых RPC — три узла. Для JSON указаны причины выбора и отличие от MessagePack.

## Запуск в Windows PowerShell

Один раз создайте виртуальное окружение и установите зависимости. Команды активации окружения и перехода в папку проекта не нужны:

```powershell
py -3.13 -m venv .venv
.\run.bat -m pip install --upgrade pip
.\run.bat -m pip install -r requirements-dev.txt
```

После этого запускайте тесты и программу через `run.bat`. Скрипт сам использует `.venv` проекта и рабочую папку проекта, даже если текущая папка PowerShell другая:

```powershell
.\run.bat -m pytest -q
.\run.bat peer_demo.py --help
```

Для запуска с увеличенными тайм-аутами задайте профиль в окне PowerShell:

```powershell
$env:OVERLAY_CONFIG = ".\config\pilot.json"
.\run.bat peer_demo.py node --port 9000 --state-dir .state\pilot-node0
```

Если PowerShell открыт не в папке проекта, вызовите скрипт полным путём, например:

```powershell
& "C:\PyCharm\overlay_p2p_coursework_scaffold\run.bat" -m pytest -q
```

В PyCharm укажите интерпретатор проекта: `.venv\Scripts\python.exe` (Settings → Project → Python Interpreter → Add Interpreter → Existing).

## Проверка обмена между двумя узлами

Откройте два терминала PyCharm в корневой папке проекта. В первом запустите серверный узел:

```powershell
.\run.bat peer_demo.py server
```

Во втором отправьте ему тестовое сообщение:

```powershell
.\run.bat peer_demo.py ping --message "Проверка связи"
```

Во втором терминале должен появиться ответ `PONG: Проверка связи`, а в первом — полученный `PING`. Остановить сервер можно сочетанием `Ctrl+C`.

## Проверка сетевого FIND_NODE

Запустите сервер с отдельной идентичностью:

```powershell
.\run.bat peer_demo.py server --state-dir .state/server
```

Скопируйте показанный сервером `NodeID`. Во втором терминале отправьте запрос, подставив скопированный 64-символьный NodeID вместо текста в кавычках:

```powershell
.\run.bat peer_demo.py find-node --target "ВСТАВЬТЕ_NODEID_СЮДА" --state-dir .state/client
```

Узел проверит, что открытый ключ отправителя соответствует его `NodeID`, и вернёт ближайшие известные контакты. Это проверка одного RPC; следующий раздел показывает поиск через несколько узлов.

## Запуск нескольких узлов и итеративный поиск

Откройте три терминала PyCharm. В первом запустите начальный узел:

```powershell
.\run.bat peer_demo.py node --port 9000 --state-dir .state/node0
```

Во втором присоедините к нему второй узел:

```powershell
.\run.bat peer_demo.py node --port 9001 --state-dir .state/node1 --bootstrap 127.0.0.1:9000
```

В третьем запустите третий узел и укажите `NodeID`, выведенный первым узлом:

```powershell
.\run.bat peer_demo.py node --port 9002 --state-dir .state/node2 --bootstrap 127.0.0.1:9001 --lookup-target "ВСТАВЬТЕ_NODEID_УЗЛА_0"
```

Третий узел сначала опросит bootstrap-узел, затем ближайших кандидатов группами до `ALPHA=3`. В выводе должны быть несколько итераций и найденный адрес. Каждый терминал продолжает обслуживать запросы; остановить узел можно сочетанием `Ctrl+C`.

Чтобы сохранить k-buckets в JSON для отчёта и проверки, добавьте параметр `--routing-export` к команде `node`:

```powershell
.\run.bat peer_demo.py node --port 9001 --state-dir .state/node1 --bootstrap 127.0.0.1:9000 --routing-export .state/exports/node1-routing.json
```

JSON создаётся сразу после bootstrap и обновляется ещё раз при остановке узла через `Ctrl+C`. В файле перечислены непустые bucket, их индексы и контакты с NodeID, адресом и временем последнего обновления. Закрытые ключи в экспорт не попадают.

## Этап 3 — публикация и поиск адресной записи

Откройте три терминала и запустите три независимых узла. Каждый узел должен оставаться запущенным.

Терминал 1:

```powershell
.\run.bat peer_demo.py node --port 9000 --state-dir .state/dht-node0
```

Терминал 2:

```powershell
.\run.bat peer_demo.py node --port 9001 --state-dir .state/dht-node1 --bootstrap 127.0.0.1:9000
```

Терминал 3:

```powershell
.\run.bat peer_demo.py node --port 9002 --state-dir .state/dht-node2 --bootstrap 127.0.0.1:9001
```

Опубликуйте подписанный `NodeRecord` от имени узла на порту 9001. Укажите каталог состояния этого же узла и номер версии:

```powershell
.\run.bat peer_demo.py publish-record --state-dir .state/dht-node1 --listen-port 9001 --bootstrap 127.0.0.1:9000 --sequence 1 --ttl 300
```

Сохраните показанный `NodeID` владельца. Найдите запись с отдельной идентичностью клиента:

```powershell
.\run.bat peer_demo.py find-value --node-id "ВСТАВЬТЕ_NODEID_ВЛАДЕЛЬЦА" --state-dir .state/dht-reader --bootstrap 127.0.0.1:9000
```

В результате должны отображаться `sequence_number`, адрес владельца и срок действия записи. В журналах узлов видны STORE-подтверждения и FIND_VALUE. Чтобы проверить отказ реплики, остановите узел на порту 9001 сочетанием `Ctrl+C` и повторите `find-value` через работающий узел на порту 9000. Запись должна найтись на одной из оставшихся реплик. При повторной публикации используйте тот же каталог владельца и увеличьте `--sequence`.

TTL задаётся в диапазоне 120–300 секунд. Повтор той же записи идемпотентен; запись с меньшим номером версии или другое значение с уже использованным номером отклоняется.

Приёмочный тест сети из пяти узлов запускается вместе с остальными тестами командой `.\run.bat -m pytest -q`. Он проверяет PING при подключении, self-lookup, остановку начального узла и последующий `FIND_NODE` между оставшимися узлами.

## Эксперимент: 30 поисков в DHT

Для измерения поиска целей, которых нет среди NodeID узлов, выполните из PowerShell:

```powershell
.\run.bat lookup_experiment.py --count 30 --output results\lookup_experiment.csv --seed 20261007
```

Эксперимент временно запускает пять локальных узлов с отдельными таблицами маршрутизации. Инициатор начинает с пустой таблицей и обращается к промежуточному узлу; каждый целевой NodeID генерируется детерминированно и отсутствует в сети. CSV содержит начальный и конечный размер таблицы инициатора, число RPC и итераций, время поиска, опрошенные NodeID и ошибки. В консоль выводится сводка, в том числе сколько поисков прошли более чем за один RPC. Ключи временных узлов удаляются после эксперимента.

## Этап 4 — защищённая сессия и проверка повторов

Новых Python-зависимостей для TLS нет: используется стандартный модуль `ssl`, а `cryptography` уже требуется этапам идентичности и DHT. Тестовый центр сертификации и сертификаты узлов автоматически создаются под `.state`; не удаляйте эту папку, пока используете те же идентичности узлов. Узлы текущего стенда запускаются на одном компьютере и доверяют локальному тестовому CA. Ограничения такой схемы описаны в `THREAT_MODEL.md`.

Сначала выполните автоматические тесты:

```powershell
.\run.bat -m pytest -q
```

Затем откройте три терминала и запустите узлы (каждый терминал должен оставаться открытым):

Терминал 1:

```powershell
.\run.bat peer_demo.py node --port 9000 --state-dir .state/stage4-node0
```

Терминал 2:

```powershell
.\run.bat peer_demo.py node --port 9001 --state-dir .state/stage4-node1 --bootstrap 127.0.0.1:9000
```

Терминал 3:

```powershell
.\run.bat peer_demo.py node --port 9002 --state-dir .state/stage4-node2 --bootstrap 127.0.0.1:9001
```

В четвёртом терминале проверьте защищённый PING/PONG:

```powershell
.\run.bat peer_demo.py ping --host 127.0.0.1 --port 9000 --message "Защищённая проверка" --state-dir .state/stage4-ping-client
```

Должен появиться ответ `PONG: Защищённая проверка`. Узел на порту 9000 должен показать полученный PING. Затем проверьте поиск через сеть:

```powershell
.\run.bat peer_demo.py find-node --host 127.0.0.1 --port 9002 --target "ВСТАВЬТЕ_NODEID_УЗЛА_0" --state-dir .state/stage4-find-client
```

Подставьте полный NodeID, показанный терминалом 1. В ответе должен быть список контактов, а среди него — NodeID узла 9000. Эти операции выполняются через TLS; raw TCP кадр не принимается как overlay RPC.

Автотесты дополнительно проверяют подмену NodeID в сертификате и payload, TLS-only настройки, повтор message ID в той же и новой сессии, а также sequence counter. Целостность сетевого ciphertext обеспечивает TLS 1.3: изменённая запись отклоняется до обработки RPC.

### Доказательство конфиденциальности в PCAP

Для приёмки этапа 4 сохраните захват loopback-трафика с помощью Wireshark и Npcap. Инструкция с командами узла и клиента находится в `PCAP_CAPTURE.md` (эта папка `docs`). В захвате должны быть видны TLS-записи на порту тестового узла, а контрольная строка прикладного сообщения не должна находиться поиском по байтам пакетов.

## Проверка идентичности узла

В корневой папке выполните команду дважды:

```powershell
.\run.bat peer_demo.py identity
```

`NodeID` и открытый ключ должны совпасть при обоих запусках. Закрытый ключ сохраняется в `.state/demo-node/identity_ed25519.key` и не должен передаваться другим узлам или добавляться в репозиторий. Для нового логического узла укажите отдельный каталог состояния через `--state-dir`.

## Контрольные результаты

Успешный запуск тестов проверяет транспорт, идентичность, поиск узлов, DHT и защищённые RPC этапа 4. Интеграционный сценарий этапа 3 публикует запись на трёх хранителях, останавливает одного из них и находит действующую запись через оставшуюся сеть.

## План зависимостей

- Сейчас: `cryptography` для Ed25519, `pytest` для тестов; TCP и JSON используют стандартную библиотеку Python.
- Позже: `matplotlib` для графиков; Docker Desktop/Compose для масштабного стенда (устанавливается отдельно, не через pip). TLS использует стандартный модуль `ssl`.

Управляющие сообщения сериализуются компактным JSON в UTF-8: этот формат входит в стандартную библиотеку и его удобно проверять при отладке. MessagePack обычно компактнее, но требует отдельной зависимости и менее удобен для просмотра. Это сравнение будет подробнее оформлено в пояснительной записке.

Версии библиотек будем фиксировать по мере подключения, чтобы воспроизвести установку на защите.
